## 2026-06-20 - [XSS Defense-in-Depth in CodeBlock]\n**Vulnerability:** Raw HTML strings generated via Shiki were rendered directly using `dangerouslySetInnerHTML` in `src/components/code-block.tsx`. While Shiki escapes output, any bypass or upstream modification to the `html` prop could result in Cross-Site Scripting (XSS).\n**Learning:** Standard `dompurify` requires a DOM environment (`window`), causing hydration mismatches and potentially failing open to unsanitized strings during Next.js SSR.\n**Prevention:** Use `isomorphic-dompurify` when sanitizing HTML strings in Next.js Server or Client Components to ensure safe SSR hydration and robust XSS protection.
## 2026-06-27 - [Security Headers Enforcement]
**Vulnerability:** The application was missing basic security headers like `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, and `Strict-Transport-Security`.
**Learning:** These headers provide important defense-in-depth protections against Clickjacking, MIME-type sniffing, and enforce HTTPS connections, reducing the attack surface.
**Prevention:** Ensured security headers are globally enforced via the `async headers()` configuration in `next.config.ts`.
## 2026-10-27 - [Client-Side vs Server-Side Route Protection]
**Vulnerability:** The `/admin` dashboard (`src/app/admin/page.tsx`) previously relied exclusively on a client-side `useEffect` and `router.push('/')` to redirect non-admin users. This allowed unauthorized users to potentially intercept the redirect, modify the JavaScript bundle, or disable JS entirely to view the Admin UI (a classic Client-Side Enforcement vulnerability).
**Learning:** In Next.js App Router, client-side authorization checks are insufficient for protecting sensitive routes because the UI payload is still delivered to the browser.
**Prevention:** Always use Server Components (`layout.tsx` or `page.tsx` on the server) with `@/utils/supabase/server` and `redirect()` from `next/navigation` to enforce authorization *before* any sensitive UI is shipped to the client.
## 2026-10-27 - [IDOR on RLS Columns]
**Vulnerability:** The RLS policy `Users can update own profile` allowed an authenticated user to update their own row in the `profiles` table. However, it did not restrict *which* columns could be updated. This allowed a malicious user to execute an update setting `isAdmin = true` on their own profile, elevating their privileges (a form of Insecure Direct Object Reference or Privilege Escalation).
**Learning:** RLS policies that allow `UPDATE` apply to the entire row by default. Without column-level security or triggers, users can modify any column on rows they are allowed to update.
**Prevention:** Use PostgreSQL `BEFORE UPDATE` triggers to inspect `current_setting('role', true)`. If the role is a client role (like `authenticated` or `anon`), force sensitive columns (like `isAdmin`) to retain their `OLD` values (e.g., `new."isAdmin" = old."isAdmin"`).
